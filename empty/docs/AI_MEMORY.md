- 【2026-08 机构换直驱曲柄摇臂 + 题目三/四整体重做 + 实机调参完整记录】球杆机构由丝杆升降换成电机直驱曲柄摇臂（±90°内旋转），触发一轮从方向标定到实机调参的完整改动，核心结论汇总如下（详细公式和数据见 `CONTROL_ALGORITHM.md` §10）：

  - **开机归零流程重写**：`app_lift_homing.c` 从"正向逼近开关→反向退让→再走固定负向偏移"改成"下降找开关（触发点即参考点）→急停→抬升 `LIFT_HOMING_LEVEL_OFFSET_PULSES` 到水平"，方向和数值都要按新机构重新实测，不能沿用旧丝杆的值（旧值相当于要求电机转 5.75 圈，直接用会撞坏新机构）。
  - **题目三整体改造**：不再是"钢珠第一阶段定位"，改为**题目四框架的完整副本**（`task3.c` 整个重写），所有参数按值复制为独立 `T3_*` 组，符合仓库【控制参数隔离规则】。原 `T3_STAGE1_*` 参数组和相关状态机、文档描述全部废弃。
  - **题目四新增两段式 K3 启动**：进题目先不动（ID1 不闭环、轮子不使能），第一次 K3 启动钢珠位置闭环并等待就绪，第二次 K3 才使能轮子发车+开始循迹+开始录像（视频录制通过新增的 `deferVideoStart` 题目表标记 + `RobotCore_NotifyTaskStarted()` 接口实现，只有题目四延迟录像开始，其余题目行为不变）；新增运行态 K3 分发机制 `RobotCore_ConfirmTask()` → 题目表 `onConfirm` 钩子（仅题目四登记，其余为 `NULL`）。
  - **修了一个真实的状态机 bug**：`T4_STATE_TIME_STOPPED` 之前没有像 `T4_STATE_FINISHED` 那样在 `OnLoop` 入口直接 `return`，会被后面的终点判定等逻辑意外拨回 `RUN`（尤其是 `FAULT_EDGE` 故障恢复握手完成时，只看 `s_wheelsStarted` 就无条件判回 `RUN`，没考虑"本次是否已经跑完"），表现为小车已经停下、蜂鸣器已响，OLED 秒表却还在走。修复：新增 `s_runCompleted` 标志 + `TIME_STOPPED` 入口直接 `return`，双重保证终止态不可逆。
  - **α-β 滤波和摩擦前馈的调参教训**：`α`/`β` 会被 `AlphaBetaFilter_Init()` 静默夹到 `[0,1]`，`β` 实用上限远低于这个硬上限（超过约 0.3 基本不滤波，超过约 0.8 实测直接导致自激振荡，UART0 日志抓到 `v=±800px/s` 的孤立噪声尖峰）；库仑摩擦前馈哪怕是个位数的小值，也会在球静止于目标附近时因为噪声导致方向随机翻转，造成电机可见颤抖（跟"球剧烈振荡"是两种不同现象，分别对应 β 过大和摩擦前馈非零）。
  - **`POS_RPM` 与 `POS_ACC` 谁是瓶颈要计算，不能凭感觉调**：每帧实际能走的脉冲数 = `min(POS_RPM, 20ms÷((256−acc)×50us))` 换算出的转速再乘脉冲/转/60000；曾经调 `POS_RPM` 完全没有效果，是因为 `acc` 早就先卡住了行程上限。
  - **新增 UART0 实时调试日志**（`app_ball_control_task.c` 的 `BALL_CTRL_DEBUG_LOG_ENABLE`，默认 0）：打印目标/测量/滤波位置/速度/命令脉冲/状态到串口，是定位上面几条教训的关键工具，排查完要记得关闭。
  - **`LEVEL_TRIM_PULSE` 稳态误差是线性、可迭代反推的**：`LEVEL_TRIM_new = LEVEL_TRIM_current + SIGN×Kx×稳态err`，一次修正量不够可以按同一公式再修一次，2~3 次内收敛，不需要精确的物理测量工具。
  - **同步更新了 CLAUDE.md、AGENTS.md、docs/FREERTOS_TASKS.md、docs/CONTROL_ALGORITHM.md** 里所有题目三"第一阶段定位"、题目四"X=320"/"6.5秒"、ID1"连杆向下"等过时表述；具体调参数值全部改成"以 taskN.c 当前源码为准"的写法，不再在文档里写死频繁变动的数字。

- 【2026-08-01 现场标定 + 钢珠控制律改摩擦前馈】用户换了更光滑的导轨后，旧的静摩擦阈值作废，且质疑"AI 给的默认值不适配我的硬件反而害我"——这个质疑是对的，本轮据此把所有猜测值换成实测值。
  - **新增标定工具**：`task6.c` 的阶梯测试（`T6_STEP_TEST_*`，步长数组从 1600 起，是旧导轨的量级）已删除，替换为**标定斜坡** `T6_RAMP_TEST_*`：从命令 0 开始每 90ms 加 20 脉冲，用视觉 X 偏移 ≥8px 自动判定"球开始动"，正负两个方向各测一次（中间 12s 让用户把球放回中间），OLED 直接显示换算好的 `B<脱离阈值> L<真实水平>`，串口同步打印 P/N/B/L 明细。以后换导轨/钢珠/摆杆几何只需重跑这个工具，不要再靠猜。
  - **实测结果（本次硬件）**：视觉 `520px/213mm = 2.441 px/mm`（球心范围 X∈[66,586]）、静止噪声仅 `±2px`、帧率 40~60fps、`B=1810 脉冲`(4.53mm 升程/1.04° 倾角)、`L=-70 脉冲`。反推 P=1740/N=1880，两方向只差 8% → **机械对称性良好，排除传动间隙**，所以 1.04° 是 V 型槽钢珠的真实滚动阻力，不是机械缺陷。旧值 3600~4000 被新导轨砍了一半多。
  - **控制律换成摩擦前馈（死区反演）**，替换掉"卡住检测+满幅夹紧"三参数（`STICTION_PULSE/STUCK_VELOCITY_PXPS/STUCK_TIME_MS` → `frictionFfPulse/ffBlendPulse`，profile 结构体同步改，task3/task4 都要跟着改初始化列表）：`pd = Kx*误差 − Kv*速度; delta = sign(pd)*B + pd`。**关键是 sign(pd) 而不是 sign(误差)**——球冲过头时 pd 变负、前馈跟着反向，刹车方向同样越过阈值，Kv 才第一次有真实制动权限；若用 sign(误差) 则 Kv 得先抵消一整个 B 才能减速，等效没有制动。
  - **旧方案为什么必然失败**（用户症状"球停在 300 反复挣扎到不了 320"的根因）：夹紧条件是"速度低于门限"，球一动（下一帧约 20ms）夹紧立刻撤销、命令掉回远低于 B 的无效值，于是球刚脱离静摩擦就失去驱动、走几像素又粘住。**更本质的一点：命令幅值低于 B 时钢珠物理上纹丝不动，所以整个线性 PD 区间原本都是无效的**——旧 `Kv=4.8` 在 60px/s 时只算出 288 脉冲，从来没产生过任何制动作用，调它等于没调。
  - **顺带修掉两个事实错误**：`BALL_CTRL_DT_MIN_SEC=0.02` 会把 60fps 的真实帧间隔(16.7ms)往上夹，使速度估计系统性偏小 20%（改 0.010）；`NOMINAL_DT` 按 30fps 写（改 1/50）。另 `FILTER_ALPHA=0.20` 当初是"为抗噪声"手调的，但实测噪声只有 ±2px，这个 α 在 50fps 下带来约 165ms 相位滞后，是动态失稳的直接来源（改 0.50）；`SETTLE_DEADBAND_PX=12` 同理改 4（≈1.6mm，取噪声两倍裕度）。
  - **⚠️ 同日修正：前馈方向一度写错成 `sign(pd)`，实测直接发散**（用户现象："第一次在 320 反转后往回冲，越冲越大、越来越刹不住"）。摩擦反抗的是【运动】，所以补偿必须跟 `sign(速度)`：`cmd = pd + B*sign(v)`，此时净驱动力恰好等于 pd。跟 `sign(pd)` 的致命之处在于 **pd 在接近目标途中会反复过零，每过零一次命令就要跳 `2*B=3620` 脉冲**，而摆杆每帧（20ms）只能走 `POS_RPM*1.067` 脉冲（100RPM→107），这一跳要 0.68 秒，摆杆永远在执行 0.68 秒前该给的倾角 → 正反馈发散。改回 `sign(v)` 后命令幅值也大幅下降（球以 +v 运动、pd=-840 时命令仅 1810-840=970，不必满幅反倾）。球接近静止时线性过渡到 `sign(pd)` 打破静摩擦，过渡带 = 新参数 `ffVelBlendPxps`（替换掉上一版的 `ffBlendPulse`）。
  - **同时修掉一个逻辑洞**：原来只要 `|误差|<死区` 就把输出清零，导致**球高速穿过目标那一刻反而放弃刹车**；现改为误差进死区【且】`|v|<=ffVelBlendPxps` 才保持。
  - **增益从此有物理依据，不用瞎试**：`a[px/s²] ≈ 0.171*脉冲`（=(5/7)g ÷400脉冲/mm ÷250mm摆杆 ×2.441px/mm）→ `ω_n=sqrt(0.171*Kx)`、`ζ=0.171*Kv/(2ω_n)`。另有两条硬约束必须一起看：**摆杆每帧行程 = POS_RPM×1.067 脉冲**，而 **Kv 放大速度噪声约 Kv×10px/s 脉冲/帧**（10px/s 是 β=0.1+位置噪声±2px 的实测量级），后者必须明显小于前者。用户为压振荡把 Kv 加到 36 反而更糟，就是因为 36×10=360 > 100RPM 时的 107，摆杆全部行程都在追噪声。当前取 Kx=12(ω_n=1.43)、Kv=18(ζ=1.08)、POS_RPM=400(427 脉冲/帧)。
  - **待办**：`BALL_CTRL_SAFE_X_MIN/MAX_PX=20/620` 在实测范围 X∈[66,586] 之外，**边缘保护永远不可能触发**，形同虚设，需按实测端点收紧；`POS_RPM=400` 仍未实测过机构上限（有无异响/失步）；ID1 负方向行程余量未知（正方向距归零开关有 17400 脉冲余量），而命令最坏可到 `B + Kx*254 ≈ 4900` 脉冲。

- 【2026-08-01 任务四钢珠 FAULT_EDGE 自动恢复】用户反馈"任务四有时候会直接退出，不继续保证钢珠在 X=320"，根因是 `app_ball_control_task.c` 的 `BALL_CTRL_INTERNAL_FAULT_EDGE`（球触边）是**单向锁存状态**：命令回水平后 `switch` 分支直接 `break`，即使调用方再次 `RequestTargetWithProfile()` 也不会清除（命令处理逻辑里 `command.enable=true` 时只有 `state==OFF` 才会重新走 `RESET_DISABLE` 序列，`FAULT_EDGE` 不是 `OFF`，落进"已运行时只更新 targetPx"分支，状态原地不动）；而 `task4.c` 原来只在 `T4_STATE_WAIT_BALL_CONTROL` 请求一次，进入 `MANUAL_BALANCE`/`RUN` 后再也不检查 `ballStatus`，所以一旦触发 `FAULT_EDGE` 就永久锁死，只能靠用户手动 K4 退出再重进（`OnExit` 的 `RequestStop()` + 人工操作菜单的自然延时够长，让内部状态机走完 `STOP→DISABLE→OFF` 两拍，凑巧能修好，掩盖了这个 gap）。**修复**：`task4.c` 新增 `T4_STATE_BALL_RECOVER_WAIT` 状态和 `s_wheelsStarted` 标志，`Task4_OnLoop()` 每拍无条件 `AppBallControl_GetStatus()`，只要不在握手状态本身且检测到 `FAULT_EDGE` 就调 `RequestStop()` 并跳到 `BALL_RECOVER_WAIT`，**必须等 `ballStatus.state==OFF` 才能重新请求**（不能一收到就立刻重发，`RequestStop` 是异步入队，立刻重发会在 BALLCTRL 处理 STOP 之前被新命令覆盖，状态机永远看不到停止指令，复现"有时候修不好"这个"有时候"的字面含义）；恢复完成后若 `s_wheelsStarted` 已为真则直接回 `T4_STATE_RUN`（不重新走轮子使能时序），否则走原有首次起步分支。命令行编译 0 Error/0 Warning。**未改动** `app_ball_control_task.c` 本身——`FAULT_EDGE` 对菜单/题目三仍是需要人工处理的保护状态，这次只让题目四自己选择自动恢复，没有放松共享模块的安全语义。

- 【2026-07-14 时钟源改为外部晶振】80 MHz 现由核心板 40MHz 外部晶振 HFXT 经 SYSPLL 倍频锁定：`HFXT 40MHz -> PDIV=/2 -> 20MHz -> QDIV=8 -> VCO 160MHz -> CLK0=/2 -> 80MHz`（PLL 结构体 `sysPLLRef=REF_HFCLK`）。关键：`rDivClk0=0` 表示 CLK0=VCO/2，不是/1；VCO=参考频率×qDiv。
- HFXT 引脚 PA5=HFXIN(`IOMUX_PINCM10`)、PA6=HFXOUT(`IOMUX_PINCM11`)，必须在 GPIO_init 里 `DL_GPIO_initPeripheralAnalogFunction` 配为模拟功能，否则不起振。范围枚举用 `DL_SYSCTL_HFXT_RANGE_32_48_MHZ`。

  - **【2026-07-15 已解决·用户实测舵机正常摆动】** 根因：TIMA0 用 DriverLib `EDGE_ALIGN`(向下计数)，CCP 输出恒为「周期起点置高、向下计到 CC 时置低」→ 高电平 = `period - CC`，写入的 CC 实际是**低电平宽度**；CC=1500 得到 18.5ms 高 / 1.5ms 低，极性反，舵机识别不了、PA8 直流被拉到 ~3V。曾把 `pwmMode` 改成 `EDGE_ALIGN_UP` 想让 CC==高电平脉宽，**实测无效**（PA8 仍 ~3V，底层原因未深究）。**最终修复**：保持 `EDGE_ALIGN`，在 `bsp_servo.c::BspServo_SetPulseUs()` 写入 `(SERVO_TIMER_PERIOD - pulseUs)` 做极性补偿，使 PA8 实际高脉冲宽度 == pulseUs；用户实测舵机正常来回摆动。教训：舵机对脉冲极性敏感，而电机 STEP 只要方波、占空比反了仍能转——所以同样 `EDGE_ALIGN` 下电机能转、舵机不动。

- 【2026-07-16 舵机1/2/3不动·根因=setCCPDirection坑】现象：4 路舵机只有舵机4(PA12/CCP3)能动，舵机1/2/3(PA8/PA9/PB4=CCP0/1/2)信号线恒 ~0.3V 不动。**根因**：`DL_Timer_setCCPDirection(gptimer, cfg)` 内部是 `gptimer->CCPD = cfg`（**整体覆盖**整个 CCPD 寄存器，不是或入一位）。原 servo 初始化分 4 次单独调用 `setCCPDirection(CC0_OUTPUT)`…`(CC3_OUTPUT)`，结果只有最后一次(CC3=0x8)留下，CCP0/1/2 退回输入态、无 PWM 输出。**修复**：四路方向必须**一次调用**把 CC0/1/2/3_OUTPUT(0x1|0x2|0x4|0x8=0xF) 全或在一起写入。单通道的电机 STEP 定时器只调一次 CC0_OUTPUT 所以没中招。教训：凡是「整体写寄存器」的 DL_setXxx，多通道/多位一定要一次性或好再写，别分多次调用互相覆盖。

- 【2026-07-16 舵机脉宽范围收窄 + 独立控制确认】
  - **范围**：安全脉宽从 600~2400us 收到 **800~2200us**（中心 1500 不变），见 bsp_servo.h。原因：常规舵机在 ~600/~2400us 两端常顶机械限位，命令了也转不到或堵转发抖发热（用户观测到极值不灵）。800~2200 留余量，仍有 ±700us≈±63° 行程，SetPulseUs 自动限幅到此区间。注意这不是 MCU 侧问题：极性补偿(period-pulseUs)在任何脉宽都精确，极值无效是舵机机械限位所致。若某舵机行程不同按需改这两个宏。

- 【2026-07-31 BALL_CTRL_POS_RPM/POS_ACC 从题目六的保守值提速】用户反馈正反两个方向速度感觉一样、整个过程很慢，问加速度该填多少。诊断：`BALL_CTRL_POS_RPM=30U` 是从题目六"转10圈慢慢量距离"标定测试直接抄来的保守值，每次 `Emm42Robot_MoveAbsolute` 调用不分方向不分距离都传这同一个常量，所以两个方向"速度一样"是必然的代码事实，不是错觉；30RPM≈1600脉冲/s≈4mm/s丝杆线速度，对实时纠偏闭环明显太慢，这才是"整个过程非常慢"的真正根因，跟加速度无关。已提到 `BALL_CTRL_POS_RPM=200`（协议层上限3000，驱动器额定3000RPM+，**这个具体机构还没在这个速度下实测过**，需要用户观察有无异响/失步）。
  - **acc 参数机制说明（容易搞反的一点）**：手册公式 `t2-t1=(256-acc)*50us`，**acc 数值越大曲线越快（越接近瞬时），数值越小（非0）越平缓**；`acc=0` 是特殊值=直接跳过曲线瞬间给全速。已把 `BALL_CTRL_POS_ACC` 从 `0` 改成 `150`，理由是复用 task2 的既有教训——轮子速度模式 `acc=0` 曾导致车身持续抖动，改用非0曲线档位(180)解决；`BALLCTRL` 每33ms刷新一次目标，`acc=0` 的瞬时冲击很可能也是"电机左右晃动"的部分成因，先给一个类似量级的中间值(150)起步。
  - 命令行编译 0 Error/0 Warning。**新的 RPM/ACC 组合实际手感（是否够快、是否还抖）待用户上板反馈**，这两个刚好是一对需要一起看的参数：RPM 决定能跑多快，ACC 决定跑多顺。

- 【2026-07-31 acc=150 实测反而更慢，纠正回 0】按题目二轮子的经验把 `BALL_CTRL_POS_ACC` 从 0 改成 150 后，用户反馈"现在明显慢得多"。用手册公式重新算账发现判断错了：`acc=150` 时爬到 `BALL_CTRL_POS_RPM=200` 需要 1 秒多（`(256-150)*50us*200≈1.06s`），但 `BALLCTRL` 每约 33ms 就刷新一次新绝对目标，曲线还没爬起来就被下一帧打断重新规划，实际能达到的速度被摁在很低的量级——比 `acc=0` 瞬时给到目标 RPM 反而慢很多。**根因是把 task2 轮子"acc=0 抖动、改非0曲线解决"的经验直接套用到了不通用的场景**：task2 是持续巡航、前后帧目标转速差很小，不需要从0重新爬升；`BALLCTRL` 是每帧一次全新的绝对位置目标，两者物理场景不同，不能照搬同一个 acc 结论。已改回 `BALL_CTRL_POS_ACC=0`，`BALL_CTRL_POS_RPM` 保持 200。**通用教训（写进了 docs/BALL_CONTROL.md）**：驱动器的曲线加减速参数是否有效，取决于"目标值在多长时间内保持不变"——巡航式命令（目标稳定、偶尔小幅调整）适合用曲线平滑；每帧刷新式命令（目标持续变化，如本项目的位置闭环）曲线经常来不及爬升就被打断，应该用 acc=0，需要平滑应该靠别的机制（但也别加软件斜坡，task2循迹早期加过软件限速斜坡导致响应变慢，后来去掉了）。
  - 命令行编译 0 Error/0 Warning。**acc=0/RPM=200 组合的实际手感待用户反馈**——如果这个组合下出现明显的机械冲击/抖动，那才是需要认真考虑软件层面斜率限制的时候，目前先不要抢先加。

- 【2026-07-31 静摩擦夹紧漏洞：瞬时低速判定导致目标附近持续振荡】用户反馈调好Kv后整体好转，但目标附近50px内来回抖动、到不了目标。诊断：静摩擦夹紧逻辑原来只看"瞬时速度是否低于阈值"就立刻满幅夹紧到`BALL_CTRL_STICTION_PULSE`，但球快到目标前`Kv`项正常刹车本来就会经过瞬间低速——这一刻被误判成"卡住"，猛地满幅推一把，把快停稳的球重新推走，形成"以为卡住→满幅踹一脚→冲过头→减速→又被当成卡住"的持续振荡循环，跟用户描述的现象完全对应。**根因数字上也能验证**：交叉点=阈值/Kx=3600/30=120px，意味着误差小于120px时`Kx*error`本来就到不了阈值，而这个范围恰好覆盖了"接近目标"的大部分区域，导致夹紧几乎必然在接近目标时被触发。
  - **修复**：新增`BALL_CTRL_STUCK_TIME_MS=150`，低速状态必须**连续**超过这个时长才真正判定为"卡住"，用`stuckStartTick`计时（球速度回升、误差回到死区内、K4重启/丢球恢复等各处都同步重置这个计时，跟`holdStartTick`的重置模式一致）。这样正常减速路过的瞬间低速不会触发夹紧，只有真正长时间静止不动才会被判定并踹一脚。
  - **通用教训**：任何"检测到某个瞬时条件就采取强力干预动作"的保护逻辑，都要考虑"这个条件是否会在正常收敛过程中被短暂触发"——如果会，必须加持续时间门限区分"真实故障状态"和"路过的正常瞬间"，否则保护逻辑本身会变成新的振荡源。这跟这个项目里`BALL_CTRL_HOLD_TIME_MS`（判定"真的稳定住了"而不是偶然一帧误差小）是同一个模式，本该在第一次实现夹紧时就用上，是这次疏漏。
  - 命令行编译 0 Error/0 Warning。**加了持续时间门限之后目标附近是否还振荡，待用户上板反馈**；如果150ms还不够，可以适当调大，但调大会让"真卡住"时的反应变慢，需要权衡。
