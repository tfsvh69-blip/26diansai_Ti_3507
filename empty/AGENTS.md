# AGENTS.md

本文件用于约束 AI 在 FreeRTOS 嵌入式项目中开发、修改和维护代码。目标不是固定某一种工程结构，而是让 AI 先理解当前项目，再按项目现有风格持续维护。

## 1. 工作原则

AI 修改项目前，必须先观察项目现状：目录结构、已有任务、消息机制、外设驱动、命名风格和文档约定。

## 2. 推荐分层

项目可按以下方向维护，但不强制要求目录名完全一致：

| 层级 | 主要职责 |
|---|---|
| `app/` | FreeRTOS 任务、业务逻辑、状态机、控制流程 |
| `module/` | 比如电机、IMU、遥控器、通信协议、传感器等可复用模块 |
| `algo/` | 比如 PID、滤波、斜坡、运动学等纯算法 |
| `bsp/` | 比如 CAN、UART、SPI、I2C、GPIO、TIM、ADC、DMA 等板级驱动 |
| `common/` | 比如公共结构体、配置、消息定义、错误码 |
| `docs/` | 比如项目说明、任务列表、消息列表、硬件接线、AI 维护记录 |

核心边界：

- `app` 决定“要做什么”。
- `module` 提供“可复用能力”。
- `algo` 只做计算，不依赖业务和硬件。
- `bsp` 只做硬件初始化、收发和回调入口。
- `common` 统一放跨模块共享定义。

## 3. 硬件与引脚规则

修改 SysConfig、GPIO、外设复用或新增硬件连接前，必须先检查引脚是否属于核心板特殊功能引脚。

尽量不要使用以下引脚；这些引脚属于特殊功能引脚，使用可能会导致核心板异常：

- A23
- A21
- A20
- A19
- A18
- A11
- A10
- A5
- A6
- A4
- A3
- A2

如果确实必须使用上述引脚，必须先在回复中说明原因、风险和需要人工确认的点，再修改相关配置或代码。

新增、删除或修改任何硬件接线、GPIO、外设复用、SysConfig 引脚配置时，必须同步更新 `docs/HARDWARE_WIRING.md`。

## 4. FreeRTOS 规则

- 任务中禁止长时间阻塞，周期循环优先使用 `vTaskDelay` 或 `vTaskDelayUntil`。
- 任务周期、栈大小、优先级应集中配置。
- ISR 中只做快速处理，复杂逻辑交给任务。
- ISR 调用 FreeRTOS API 时必须使用 `FromISR` 版本。
- 不要在高频任务、控制环或中断中动态分配内存。
- 任务间共享数据必须考虑同步、互斥、临界区或消息传递。
- 控制输出前必须检查 enable、离线、超时和限幅。

## 5. 通信规则

跨应用、跨任务通信优先使用消息机制，例如：

```c
PubPushMessage(pub, &msg);
SubGetMessage(sub, &msg);
```

若项目已有 message center、queue、event group、stream buffer 或 mailbox，优先沿用现有机制。

原则：

- 应用之间尽量不要互相包含头文件形成强耦合。
- 不要用全局变量直接传递业务数据。
- 新增跨模块消息时，应放到项目已有的公共消息定义文件中。
- 修改消息结构体时，同步更新消息说明文档。

## 6. 新功能放置原则

新增功能时，先判断它属于哪一类：

| 需求类型 | 应优先放置 |
|---|---|
| 控制模式、状态机、任务流程 | `app/` |
| 电机、传感器、协议解析 | `module/` |
| PID、滤波、数学解算 | `algo/` |
| 外设初始化、收发、中断回调 | `bsp/` |
| 配置宏、消息结构体、公共类型 | `common/` |
| 项目说明、任务/消息/硬件接线记录 | `docs/` |

如果一个改动需要跨很多层，必须先说明原因，并尽量保持接口清晰。

## 7. AI 维护文档

AI 在修改项目时，应维护以下文档。若项目已有同类文件，沿用原文件；若没有，可按需要创建：

| 文档 | 用途 |
|---|---|
| `docs/PROJECT_CONTEXT.md` | 当前项目架构、硬件、主要模块、关键约定 |
| `docs/FREERTOS_TASKS.md` | 任务名、周期、优先级、栈大小、输入输出 |
| `docs/MESSAGE_LIST.md` | 消息名、结构体、发布者、订阅者、用途 |
| `docs/HARDWARE_WIRING.md` | 硬件名称、信号、连接引脚、电气说明、排查备注 |
| `docs/AI_MEMORY.md` | 用户固定要求、重要决策、踩坑记录、后续注意事项 |

`AI_MEMORY.md` 只记录长期有用的信息，不记录一次性聊天内容。

## 8. 修改代码后的检查

每次改完代码，AI 必须自查：

- 是否符合项目现有架构？
- 是否破坏分层边界？
- 是否引入了不必要的全局变量？
- 是否遗漏 FreeRTOS 同步和中断安全？
- 是否遗漏离线、超时、失能、限幅保护？
- 是否新增了未记录的任务、消息、模式或配置？
- 是否需要更新 `docs/` 下的维护文档？
- 是否保持已有接口兼容？
- 是否误用了核心板特殊功能引脚？
- 是否需要更新 `docs/HARDWARE_WIRING.md`？
- 关键代码是否写了必要的中文注释？

## 9. 输出要求

AI 每次完成修改后，应简要说明：

1. 修改了哪些文件。
2. 为什么这样放置代码。
3. 是否更新了任务、消息、硬件接线或项目记忆文档。
4. 代码运行或烧录后应该出现什么现象，方便用户对照排查。
5. 还有哪些风险或需要人工确认的点。

总原则：先理解项目，再按现有结构维护；少做无意义重构，多保持嵌入式项目可控、清晰、稳定。
